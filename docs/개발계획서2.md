# 부산 기회 추천(B 파트) 개발명세서

2026년 11월 20일 · @상원 · rev 55

## 1. 개요

B 파트는 전국 채용공고를 보여주되, 수도권 공고를 비교하는 순간 같은 일을 하는 부산 공고와 부산 정책이 함께 보이게 만든다. 판정·점수·정렬은 규칙 코드로 하고, LLM은 공고 요건 추출과 설명 문장에만 쓴다.

| 항목 | 내용 |
| --- | --- |
| 기능명 | 부산 기회 추천: 채용공고·청년정책 맞춤 추천 (제안서 4.2) |
| 목적 | 부산 선택지를 비교 순간에 보여주고, 부산 정책을 신청까지 챙기게 해서 부산 취업·정착을 스스로 고르게 돕는다 |
| 사용자 | 부산 청년: 부산 소재 대학 재학·졸업(예정)자, 부산 거주 구직자 |
| 방식 | 툴 우선. 같은 함수를 REST API(프론트용)와 통합 Agent(A 담당 Bedrock Agent)의 Action Group, 두 입구로 쓴다 |
| MVP 범위 (P0) | 공고·정책 수집과 정제, 맞춤 공고 피드(전국, 부산 우선 정렬), 공고 상세(지원 자격·배지·지역인재), 같은 일 부산 대안, 나란히 비교, 이유 질문, 정책 지갑, 저장·목표 담기, 알림(알림함·메일), Action Group 조회 툴 |
| 시간 되면 (P1·P2) | 새 부산 공고 실시간 매칭, 주간 리포트, 외부 공고 붙여넣기 분석, 취업행사, 공공기관 서류 준비도(1~9칸), 부산시 리포트 |
| MVP 제외 | 기업 관계 그래프 화면(데이터만 제공 가능), 다른 채용 사이트 크롤링, 시연 중 공공 API 실시간 호출. 2차 기능(해커톤 이후): 기업 파트타임 공고, 학교 인턴 매칭 |
| 담당 구분 | 박상원: 수집·정제, 추천·유도 규칙, 정책 매칭, 알림, B API, Action Group, B 테이블 · 프론트: 피드·상세·비교·정책 지갑·알림함 화면과 문구 · 공통 백엔드: API Gateway, Cognito, 배포, 공통 프로필 · A: 통합 Agent에 Action Group 연결, CareerProfile 제공 · C: 목표 공고로 모의면접 시작 |

### 1.1 개발 방향

1. 툴을 먼저 만든다. 같은 함수가 지금은 REST API로, 동시에 A의 통합 Agent에서 Action Group으로 불린다. 툴을 에이전트로 감싸는 비용은 작고, 반대는 크다.
2. 공공 데이터는 새벽에 모아 DynamoDB에 둔다. 툴은 저장된 데이터만 읽고, 시연 중에는 공공 API를 부르지 않는다.
3. 개입은 결정 순간에만 작게 한다. 정렬, 같은 일 부산 대안, 나란히 비교, 정책 안내 네 가지뿐이다.
4. 서울과 부산은 같은 데이터, 같은 함수로 계산한다. 서울이 이기는 칸도 그대로 보여준다.
5. AWS 서비스는 이유가 있는 곳에 쓴다: 수집 파이프라인, 벡터 검색, 사용자별 일정 예약, 이벤트 기반 알림.

기획 근거는 세 줄로 요약된다. 유출은 공고를 비교하는 순간에 일어난다. 비교 순간에 부산 장점이 안 보이는 보임 격차와, 정책을 알아도 신청까지 안 가는 실행 격차를 메운다.

### 1.2 제안서와 맞춘 방향

| 제안서 문장 | 이 명세의 구현 |
| --- | --- |
| 1.3 무조건 부산에 남도록 유도하지 않고 자발적 선택을 지원 | 유도는 정렬·대안·비교·정책 안내로만 한다. 막거나 숨기는 화면은 없다 |
| 3.2 부산 근무 공고 중심 추천, 타 지역 공고와 비교 가능 | 기본 범위는 전국, 기본 정렬은 부산 우선 |
| 3.2 부산 소재 여부만으로 직무 적합도를 왜곡하지 않음 | 적합도(matchScore)에는 부산 가산점을 넣지 않는다. 가산점은 정렬 점수(rankScore)에만 넣는다 |
| 3.2 본사 소재지와 실제 근무지 구분 | 부산 여부는 근무지로 판단하고, 본사 소재지는 따로 저장한다 |
| 7.3 결정적 처리는 규칙, 생성형 AI는 비정형 분석·설명 | 판정·점수·배지·날짜는 코드, LLM은 추출·설명만 |
| 8.2 공고 원문의 외부 지시를 실행 명령으로 취급하지 않음 | 공고 텍스트는 태그로 감싸 데이터로만 넘기고, 출력은 스키마로 검사한다 |

### 1.3 유도 원칙을 구현 규칙으로

"티 안 나게"는 사용자가 밀린다고 느끼지 않을 만큼 자연스럽고, 구조를 알게 돼도 속았다고 느끼지 않는 것으로 정의한다.

| 원칙 | 구현 규칙 | 확인 |
| --- | --- | --- |
| 선택권 보장 | 정렬 기준을 작은 칩으로 표시하고 한 번에 끌 수 있다. 공고를 숨기지 않는다 | T-01 |
| 사실만 | 배지·숫자에 출처(source)와 기준일(asOf)이 없으면 응답에서 뺀다. LLM 문장의 숫자는 사실 목록에 있는 것만 | T-08, T-19 |
| "당신에게 유리"로 말하기 | 문구를 사용자 조건과 연결한다. 예: 부산 소재 학교 졸업 예정이라 지역인재 전형 대상일 수 있어요 | 4.7 문구 규칙 |
| 부산 쪽 길을 더 쉽게 | 정책 지갑, 지역인재 판정, 목표 담기 때 마감·정책 일정 자동 등록 | B-08~B-10 |
| 결정 순간에만, 적게 | 미니 카드 최대 2개, 이유 질문 1회, 즉시 알림 주 2회 이하 | T-09, T-11 |

하지 않을 것은 다섯 가지다. 수도권 공고 숨기기·불리하게 표시, 가짜 숫자·가짜 긴급함, 사실과 다른 손실 문구, 정책 비교에서 부산 쪽만 계산, 검수 안 된 정책 노출. 코드 리뷰와 테스트의 기준으로 쓴다.

## 2. 아키텍처

B는 네 흐름으로 돈다: 새벽 수집, 화면 요청, 알림, 통합 Agent 호출. 네 흐름은 같은 DynamoDB와 S3 Vectors를 읽고, 공공 API는 새벽 수집에서만 부른다.

[embedded content: B 파트 구성도 · 4개 흐름이 데이터 한 곳을 공유]

공공 API는 새벽 수집에서만 부르고, 화면·통합 Agent·알림은 같은 테이블과 벡터 인덱스를 읽는다. Step Functions와 Streams 매칭은 P1이고, 처음에는 수집 Lambda를 직접 실행한다.

### 2.1 처리 흐름

1. **새벽 수집** (매일 04:30 KST): EventBridge Scheduler가 Step Functions를 실행한다. 출처별 수집 Lambda가 원본을 S3에 저장하고, 정규화·중복 제거 후 DynamoDB에 넣는다. 바뀐 공고만 보강(요건 추출, 임베딩, 배지, 지역인재)하고, 수도권 공고마다 부산 대안 후보를 미리 계산한다.
2. **피드 요청**: 프로필을 읽고 후보를 두 번 찾는다(부산 필터 한 번, 전국 한 번). 규칙 점수로 정렬하고 배지와 근거 사실을 붙인다. 이 경로에는 LLM이 없다.
3. **수도권 공고 열기**: 미리 계산한 부산 후보를 이 사용자 기준으로 다시 정렬해 미니 카드 2개를 보여준다. 비교 패널은 두 지역을 같은 함수로 계산한다.
4. **첫 수도권 저장**: 응답의 askLeaveReason이 true면 프론트가 이유 질문을 한 번 보여준다. 답은 대안 정렬에 반영한다.
5. **정책 지갑**: 규칙 엔진이 정책마다 판정과 이유를 만든다. "열리면 알림"을 누르면 일회성 일정을 만든다.
6. **일정 실행**: opp-notifier가 실제로 열렸는지 다시 확인하고 알린다. 아직이면 7일 뒤 재확인 일정을 만든다.
7. **통합 Agent**: A의 Career Mentoring Agent가 BusanOpportunity Action Group을 부르면 opp-api와 같은 코드가 사실 목록을 돌려준다.

### 2.3 주요 결정

| 결정 | 이유 |
| --- | --- |
| 툴 먼저, 같은 함수를 REST와 Action Group 두 입구로 | 툴 → 에이전트 전환은 싸고 반대는 비쌈. 팀 통합 Agent(A)에 바로 붙음 |
| 시연 중 공공 API 실시간 호출 안 함 | 응답 지연·일일 한도·장애. 툴은 저장된 데이터만 읽음 |
| matchScore와 rankScore 분리 | "부산 여부로 적합도 왜곡 금지"를 지키면서 정렬만 유도 |
| 가산점 0.06 < 역전 금지 폭 0.15 | 0.06보다 더 잘 맞는 비부산 공고는 구조적으로 뒤로 밀리지 않음. 설정 로딩 때 검사 |
| 후보 검색을 "부산 한 번 + 전국 한 번" | 부산 공고가 후보에서 빠지는 일을 막음(보임 격차). 순서는 점수로 정함 |
| 부산 대안은 수집 때 공고 기준으로 미리 계산, 사람별 순서는 요청 때 | 피드 응답 속도 |
| 목록에는 LLM 없음, 설명 문장은 상세에서 별도 호출 | 속도·비용, 화면이 LLM을 기다리지 않음 |
| 요건 구조화는 데모 직무군의 부산·수도권 공고만 미리, 나머지는 상세를 열 때 1회 | Bedrock 한도와 수집 시간 |
| 정책 비교는 두 지역 모두 온통청년 출처만 합산 | 부산만 시드로 보강하면 비교가 기울어짐. 시드는 지갑에만 씀 |
| verified=false 정책과 출처 없는 상수는 노출 안 함 | 틀린 금액·조건 방지 |
| userId는 인증 정보와 Agent sessionAttributes에서만 읽음 | 모델이 다른 사용자 데이터를 조회하지 못하게 |
| 모든 날짜 계산은 asOf를 받음 | 테스트와 데모 "시간 앞당기기" |
| 리전 ap-northeast-2, 모델 ID는 환경변수 MODEL_ID (B는 임베딩용 EMBEDDING_MODEL_ID를 더 씀) | 팀 규칙 (C 명세와 같음) |

## 3. 사용 데이터

공고·정책·코드·월세는 공공 API로 모으고, 청끌기업·이전기관·정책 시드·지역 통계는 직접 정리한다. 모든 값은 출처와 기준일을 달고 들어오며, 원본 응답은 S3에 그대로 남긴다.

### 3.5 데이터 원칙

- 모든 공고·정책·통계는 source, sourceUrl, collectedAt 또는 asOf를 가진다.
- 원본 응답은 S3 raw/{출처}/{날짜}/에 그대로 둔다. 재처리와 데모 고정에 쓴다.
- postingId(팀 스키마의 jobPostingId)는 출처와 원본 번호로 고정한다. 내용이 바뀌면 새 스냅샷을 쌓고, contentHash가 같으면 보강을 건너뛴다.
- 부산 여부는 근무지로 판단한다. 근무지가 없으면 "근무지 확인 필요"로 두고 부산으로 세지 않는다.
- 값마다 extractedBy(API, LLM, MANUAL)를 남긴다. API 값이 있으면 LLM으로 덮어쓰지 않는다.
- LLM은 원문에 있는 내용만 뽑고 근거 문장(quote)을 함께 저장한다.
- 이용 조건(저장·재배포)을 확인하고, 공고 원문 전체를 다른 곳에 다시 내보내지 않는다.

### 4.2 P0 기능 명세

#### B-01 데이터 수집·정제

1. Secrets Manager에서 키를 읽고 5분 캐시한다.
2. 목록 API를 페이지마다 부르고 원본을 S3에 저장한다. 실패한 페이지는 지수 백오프로 3번까지 다시 부른다.
3. 상세 API는 데모 직무군의 부산·수도권 공고에만 부른다. 일일 한도를 확인하기 전까지의 제한이다.
4. 공통 스키마로 바꾼다: 지역 코드 → sido·sigungu, 급여 → 만 원/년, "채용시까지" → rolling=true.
5. contentHash가 바뀐 공고만 새 스냅샷(SNAP#)을 쓰고 LATEST를 바꾼 뒤 needsEnrich를 표시한다.
6. 마감이 지난 공고는 LATEST의 isExpired를 true로 바꾼다. 스냅샷은 지우지 않는다(팀 스키마).
7. 출처별 건수·실패를 S3 runs/와 CloudWatch 지표로 남긴다.

완료 기준: 부산 공고, 수도권 데모 직무군 공고, 공공기관 공고, 정책(부산·서울·전국)이 적재된다. 같은 날 두 번 돌려도 건수가 같다.

#### B-02 공고 보강

- 요건 추출(경량 LLM): 공고 텍스트를 <posting> 태그로 감싸 데이터로만 넘긴다. 출력은 Pydantic 모델(required, preferred, certificates, majors, educationMin, careerType, remoteWork, selectionSteps, documents, evidence)로 검사한다. 1번 다시 시도해도 실패하면 extractStatus=FAILED로 두고 원문 링크만 보여준다.
- API에 있는 값(마감일·근무지·급여)은 LLM으로 덮어쓰지 않는다.
- 임베딩: "직무명 | 제목 | 업무 설명 | 필수 | 우대"를 벡터로 만들어 S3 Vectors의 postings 인덱스에 넣는다. 필터 키는 isBusan, sido, jobMajor, active, deadline이다.
- 배지: 청끌기업(이름 정규화 + 사업자번호), 강소기업, 이전기관, 원격 근무. 배지마다 source와 asOf를 단다.
- 지역인재: 이전기관 공고이고 공고문에 지역인재 전형·가점이 나오면 LIKELY, 이전기관인데 언급을 못 찾으면 CHECK_NEEDED.
- 부산 대안 후보: 수도권 데모 직무군 공고마다 부산 후보 상위 10개를 유사도와 함께 저장한다.

완료 기준: 정답 20건 기준 필수·우대 구분 정확도 90% 이상, 추출 실패율 5% 미만.

#### B-03 맞춤 공고 피드 (search_postings)

입력: userId(인증 정보), region(ALL 기본, BUSAN, CAPITAL, 시·도 코드), sort(BUSAN_FIRST 기본, MATCH, DEADLINE, RECENT), jobCodes(기본은 희망 직무), cursor, limit(기본 20).

1. 프로필을 읽는다: 공통 프로필, B 설정, 있으면 A의 CareerProfile 기술·자격증.
2. 프로필 벡터를 만든다(희망 직무·전공·기술 텍스트, 24시간 캐시).
3. 후보를 모은다: S3 Vectors 질의 두 번(부산 필터 상위 30, 전국 상위 30, 둘 다 진행 중 공고) + 희망 직종 GSI 보충, 중복 제거.
4. matchScore를 계산한다(4.5). 부산 가산점은 없다.
5. rankScore로 정렬한다. 가산점은 sort=BUSAN_FIRST일 때만 붙는다.
6. 배지, 근거 사실(facts), 지원 자격 상태를 붙이고, 수도권 공고에는 busanAlternativesCount를 붙인다.
7. 응답에 ranking.basis(정렬 기준 문구)와 dataAsOf를 넣는다.

완료 기준: BUSAN_FIRST와 MATCH의 공고 집합이 같다. 0.15 이상 더 잘 맞는 비부산 공고는 부산 공고보다 위에 있다. p95 1.5초 이내.

#### B-04 공고 상세 (get_posting)

- 출력: 구조화 요건, eligibility(조건별 MET·NOT_MET·UNKNOWN), badges, regionalTalent, relatedPolicies(이 공고에 취업하면 받을 수 있는 부산 정책), 수도권 공고면 대안 미리보기 2개.
- 지원 자격 규칙: 학력(요구 ≤ 보유), 경력(신입·무관), 필수 자격증(보유 여부), 전공(명시적 필수일 때만). 정보가 없으면 UNKNOWN이고 감점하지 않는다.
- 설명 문장은 GET /postings/{id}/explanation으로 따로 부른다. 사실 목록으로 2문장을 만들고 24시간 캐시하며, 숫자 대조와 금지 문구 검사를 거친다.
- 필수 조건을 못 맞춘 공고도 숨기지 않고 이유를 붙여 보여준다.

#### B-05 같은 일, 부산에서 (find_busan_alternatives)

입력: postingId(비부산 공고), leaveReason(선택, 없으면 저장된 값).

1. 미리 계산한 후보를 쓰고, 없으면 S3 Vectors를 바로 질의한다(isBusan=true, 진행 중).
2. 유사도 0.70 이상만 남긴다.
3. altScore(4.5)로 정렬해 상위 3개를 고른다.
4. 0개면 직종 상위 분류로 한 단계 넓혀 유사도 0.60 이상으로 다시 찾는다. 그래도 0개면 noAlternative=true로 알림 구독을 제안하고 NO_ALTERNATIVE 이벤트를 남긴다.

출력: alternatives(최대 3개, facts·whyShown 포함), expanded, noAlternative. 부산 공고를 넣으면 빈 목록과 reason=ALREADY_BUSAN을 돌려준다.

완료 기준: 페르소나 ①의 서울 데이터 분석 공고에서 2개 이상, 모두 부산 근무, 유사도 0.70 이상.

#### B-06 나란히 비교 (compare_postings)

| 행 | 계산 | 규칙 |
| --- | --- | --- |
| 급여 | 공고 기재값 | 두 공고 모두 적혀 있을 때만 비교, 아니면 "공고에 없음" |
| 주거비 | 근무지 구의 원룸 환산 월세 중앙값 | 표본 30건 미만이면 시·도 값으로 바꾸고 표시. 계산식 공개 |
| 생활비 반영 | 세전 월 급여(공고 하한) − 월 주거비 | 기본 꺼짐. 급여를 비교할 수 있을 때만 |
| 가족과 거주 | 켜면 부산 주거비 0 | 사용자 토글, 저장하지 않음 |
| 통근 | 지역 평균 | 출처가 있을 때만, "지역 평균" 표시 |
| 지역 정책 | 같은 규칙 엔진으로 서울 가정·부산 가정을 각각 계산 | 온통청년 출처만 합산, 전국 공통 정책은 "어디서든 같음 N개" |
| 지역인재 | 이전기관 공고일 때만 | 학교 소재지 기준 "대상일 수 있음" |
| 인증 | 청끌기업·강소기업 | 해당 없으면 "-" |

승패 표시는 하지 않고 값만 나란히 둔다. 완료 기준은 서울이 높은 칸이 그대로 보이고, 두 지역 정책이 같은 함수로 계산되는 것이다.

#### B-07 이유 질문 (set_preferences)

- 트리거: 수도권 공고를 처음 저장할 때, 지역 필터를 수도권으로 처음 바꿀 때. 서버가 askLeaveReason=true를 사용자당 한 번만 내려준다.
- 선택지: SALARY, NO_JOB_IN_BUSAN, GROWTH, WORK_LIFE, HOUSING, WANT_SEOUL_LIFE, SKIP. 설정에서 바꿀 수 있고 다시 묻지 않는다.
- 재정렬 규칙은 4.6에 있다.

#### B-08 정책 지갑 (match_policies)

판정 규칙:

- 나이: 생년만 받으므로 만 나이가 범위 경계에 걸치면 CHECK_NEEDED.
- 거주: 정책 지역에 사용자 시·도나 구가 있거나 전국이면 충족.
- 취업 상태: 정책 대상에 들어가거나 제한이 없으면 충족.
- 소득: 조건이 있는데 입력하지 않았으면 CHECK_NEEDED.
- 중복 불가: 받는 중이라고 표시한 정책과 겹치면 NOT_ELIGIBLE.
- 자유 서술 조건은 판정에 쓰지 않고 "직접 확인할 조건"으로 보여준다.

분류는 OPEN_NOW(지금 신청 가능), NEXT_CYCLE(다음 모집 예정, 작년 일정 기준), AFTER_EMPLOYMENT(취업하면), SETTLEMENT(정착하면), CLOSED(접어 둠)다. 합계는 자격만 맞으면 받는 금액(guaranteedIfEligible)과 선정돼야 받는 최대 금액(selectiveMax)으로 나누고, 본인 저축분은 더하지 않는다.

정책마다 판정, 이유 목록, 혜택(시 지원분·본인분), 신청 기간, 선정 방식, 작년 경쟁률, 중복 불가 정책, 체크리스트, 원문 링크를 보여준다. 완료 기준은 페르소나 3명의 기대 결과와 일치하고 verified=false 정책이 보이지 않는 것이다.

#### B-09 저장·목표 담기 (add_target_posting)

- 입력: postingId, kind(INTEREST, TARGET), fromAlternativeOf(대안 카드에서 저장했으면 원래 공고 ID), Idempotency-Key 헤더.
- 조건부 쓰기로 한 번만 저장한다. TARGET이면 마감 D-7·D-3 일회성 일정을 만든다. 일정 이름은 사용자·공고 해시로 고정해 64자 안에 두고, 같은 이름이 이미 있다는 오류는 성공으로 처리한다(오류 코드는 첫 테스트에서 확인).
- 수도권 첫 저장이면 askLeaveReason=true를 돌려준다. PostingSaved 이벤트는 P1에서 발행한다.
- 상태: INTEREST → PLANNED(지원 예정) → PREPARING(준비 중) → APPLIED(지원 완료) → RESULT(결과 확인). 제안서 4.9의 상태와 맞춘다.

#### B-10 알림 (check_new_opportunities, opp-notifier)

- 종류: POLICY_OPEN, POLICY_CLOSING(D-3), TARGET_DEADLINE(D-7·D-3), NEW_BUSAN_SIMILAR(P1), WEEKLY_REPORT(P1).
- 일정이 울리면 실제 상태를 다시 확인한다. 조건이 맞으면 알리고, 아니면 7일 뒤 재확인 일정을 만든다(최대 4번).
- 상한: 즉시 알림 주 2회, 나머지는 하루 1회 요약(09:00). 22시~8시에는 보내지 않는다.
- 중복 방지: notificationId = 해시(userId·종류·대상·날짜), 조건부 쓰기.
- 채널: 알림함(항상), 메일(동의한 사용자, SES).
- 데모: POST /admin/demo-clock으로 asOf를 앞당기면 그 사이에 울릴 일정을 바로 실행한다. 화면에 "시뮬레이션"이라고 표시한다.

B-11 Action Group은 5.9에서 다룬다.

### 4.4 고정 규칙

- matchScore에 부산 가산점을 넣지 않는다. 화면에는 숫자 대신 "잘 맞아요 / 맞는 편이에요 / 조금 맞아요" 3단계로 보여준다. A의 서류 적합도(fitScore)와 헷갈리지 않게 하려는 것이다.
- 가산점은 matchScore 0.5 이상인 부산 근무 공고에만, sort=BUSAN_FIRST일 때만 준다.
- 설정을 읽을 때 busanBoost < inversionGuard, 가중치 합 = 1을 검사한다.
- 미니 카드 최대 2개, 대안 화면 최대 3개, 유사도 0.70 미만은 보여주지 않는다.
- 이유 질문은 사용자당 1회, 즉시 알림은 주 2회 이하다.
- 출처·기준일이 없는 배지·숫자는 응답에서 빼고, verified=false 정책은 보여주지 않는다.
- 공고는 숨기지 않는다.

### 4.5 점수 계산

```latex
\mathrm{match} = \frac{\sum_{i \in M} w_i c_i}{\sum_{i \in M} w_i}, \qquad \mathrm{rank} = \mathrm{match} + 0.06 \cdot [\mathrm{Busan} \wedge \mathrm{match} \ge 0.5], \qquad \mathrm{alt} = 0.6\,s + 0.25\,\mathrm{match} + 0.15\,r
```

M은 측정할 수 있는 항목, s는 두 공고의 유사도, r은 이유 적합도(4.6 조건에 맞으면 1, 아니면 0)다.

| 항목 | 가중치 | 계산 |
| --- | --- | --- |
| 직종 일치 (jobMatch) | 0.35 | 희망 직무와 직종 세분류 일치 1.0, 같은 중분류 0.6, 같은 대분류 0.3, 그 외 0 |
| 직무 내용 유사도 (contentSim) | 0.30 | 프로필·공고 벡터의 코사인 값을 하한 0.20, 상한 0.80으로 0~1 변환 |
| 필수 조건 (requiredOk) | 0.20 | 확인 가능한 필수 조건 중 충족 비율, UNKNOWN은 0.5 |
| 선호 조건 (preferredOk) | 0.15 | 우대 조건 일치 비율과 사용자 중요 조건 충족 비율의 평균 |

측정할 수 없는 항목은 빼고 나머지 가중치로 다시 나눈다. A의 적합도 계산, C의 종합 점수와 같은 방식이다. 화면 3단계는 0.70 이상, 0.50~0.70, 0.50 미만이다. 코사인 하한·상한과 유사도 기준 0.70은 임베딩 모델을 정한 뒤 비슷한 공고 쌍 20개, 다른 쌍 20개로 조정한다.

### 5.9 Action Group (통합 Agent 연결)

| 항목 | 내용 |
| --- | --- |
| 이름 | BusanOpportunity |
| 붙는 곳 | A 담당 Career Mentoring Agent (Bedrock Agents) |
| Lambda | opp-agent. opp-api와 같은 코드이고 핸들러만 다르다 |
| 스키마 | OpenAPI 3.0. Powertools의 BedrockAgentResolver가 코드에서 만든다 |
| 사용자 식별 | sessionAttributes.userId (A 백엔드가 InvokeAgent 때 넣음). 스키마에는 userId 파라미터가 없다 |

| 경로 | Agent가 읽는 설명 | 파라미터 |
| --- | --- | --- |
| GET /agent/postings | 사용자에게 맞는 채용공고를 찾는다. 비슷하게 맞으면 부산 근무 공고를 먼저 돌려준다 | keyword, region(ALL, BUSAN), limit ≤ 5 |

Action Group 하나에는 API를 11개까지 넣을 수 있고 Lambda는 하나다. 응답 크기 한도는 Lambda 동기 응답 한도와 같다 ([Bedrock 문서](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-lambda.md)). 사용자 확인은 OpenAPI 스키마의 x-requireConfirmation으로 켠다 ([스키마 문서](https://docs.aws.eu/bedrock/latest/userguide/agents-api-schema.html)). Powertools는 OpenAPI 방식과 Function details 방식을 모두 지원한다 ([Powertools 문서](https://docs.aws.amazon.com/powertools/python/3.22.0/core/event_handler/bedrock_agents/)).

스키마는 agent.get_openapi_json_schema()로 뽑아 schema.json으로 저장하고, API가 바뀌면 다시 뽑아 Agent를 갱신한다. 저장 경로에는 openapi_extensions={"x-requireConfirmation": "ENABLED"}를 붙인다.

비즈니스 함수는 하나이고, 입구만 둘이다.

```python
from aws_lambda_powertools.event_handler import APIGatewayRestResolver, BedrockAgentResolver
from opportunity.core.alternatives import find_busan_alternatives  # 비즈니스 함수 하나

rest = APIGatewayRestResolver(enable_validation=True)
agent = BedrockAgentResolver()

@rest.get("/api/v1/opportunities/postings/<posting_id>/alternatives")
def rest_alternatives(posting_id: str):
    user_id = rest.current_event.request_context.authorizer.claims["sub"]
    return find_busan_alternatives(user_id, posting_id).model_dump()

@agent.get("/agent/postings/<posting_id>/alternatives",
           description="수도권 공고와 하는 일이 비슷한 부산 공고를 찾는다.")
def agent_alternatives(posting_id: str):
    user_id = agent.current_event.session_attributes["userId"]  # 모델 파라미터로 받지 않음
    return find_busan_alternatives(user_id, posting_id).compact()
```

A의 Agent 지시문에 넣을 문장은 아래와 같다.

> 부산 공고·청년 정책 질문에는 BusanOpportunity 도구를 쓴다. 사용자가 수도권 공고를 이야기하면 비슷한 부산 공고가 있는지 확인하고, 있으면 한 번만 짧게 알려준다. 사용자가 원하지 않으면 다시 권하지 않는다. 도구가 준 사실과 숫자만 말하고, 지역을 바꾸면 손해라는 식으로 말하지 않는다.

## 6. DB 모델과 설정 파일

B는 새 테이블을 만들지 않고 팀 공통 DB 스키마(백엔드 초안 v1.0, 2026-11-20, 팀 합의 전)를 쓴다. 공고·정책·기업은 team07-catalog에, 사용자별 B 데이터는 team07-career-mentor의 USER#{userId} 아래에 둔다. 키 이름은 범용(PK, SK, GSI1PK, GSI1SK)이고 모든 아이템에 entityType, schemaVersion, createdAt, updatedAt을 넣는다. Scan은 쓰지 않고 GetItem·Query로만 읽는다. API의 postingId는 스키마의 jobPostingId와 같은 값이다.

### 6.1 공고·정책·기업 (team07-catalog)

| 아이템 | PK / SK | GSI1PK / GSI1SK | B가 넣는 값 |
| --- | --- | --- | --- |
| 공고 스냅샷 | POSTING#{jobPostingId} / SNAP#{snapshotId} | — | 스키마 값: requirements[].sourceQuote, eligibilityRules[], closesAt, officialUrl, sourceType, checkedAt. B 값: source, company, workRegion, job, employmentType, salary, jobDescription, remoteWork, selectionSteps, documents, badges, regionalTalent, extractStatus, extractedBy, contentHash |
| 공고 최신 | POSTING#{jobPostingId} / LATEST | POSTING#{시도코드} / closesAt | 스키마 값: snapshotId, title, organization, isExpired, isSample. 목록용 B 값(추가 요청): isBusan, isCapitalArea, workRegion, job, salary, remoteWork, badges |
| 부산 대안 후보 (추가 요청) | POSTING#{jobPostingId} / ALTS | — | candidates[{jobPostingId, similarity}], computedAt |
| 청년정책 | POLICY#{policyId} / META | POLICY#{시도코드} / applyEnd | 스키마 값: title, summary, amountMax, ageMin, ageMax, residenceRule, incomeRule, applyStart, applyEnd, url, source. B 값: kind, regions, category, stage, eligibility, benefit, application, lastCycle, exclusiveWith, checklist, verified, verifiedBy, verifiedAt, youthcenterId |
| 기업 | COMPANY#{companyId} / META | COMPANY#{시도코드} / name | 청끌기업·강소기업·이전기관 시드. highlights[]에 인증 종류, source·asOf |

- 수집: contentHash가 바뀐 공고만 새 SNAP#을 쓰고 LATEST를 바꾼다. snapshotId는 {수집일}-{contentHash 앞 8자}다. 원문이 같으면 요건 추출 결과는 같은 스냅샷에 한 번만 채운다.
- 마감: TTL을 쓰지 않는다. 마감이 지나면 LATEST의 isExpired를 true로 바꾸고 스냅샷은 남긴다.
- GSI 정렬 키가 없으면 인덱스에서 빠지므로 상시 채용의 closesAt, 상시 정책의 applyEnd는 9999-12-31로 둔다.
- 전국 정책은 POLICY#00, 구 단위 정책은 시·도 키(POLICY#26)에 두고 regions로 거른다.
- sourceType은 공공 API 수집분이 OFFICIAL, 직접 정리한 데모 공고가 DEMO다. DEMO는 isSample=true이고 화면에 "데모 데이터"를 표시한다.
- 바뀐 이름: deadline → closesAt, sourceUrl → officialUrl(정책은 url), collectedAt → checkedAt, company.name → organization, active → isExpired(뜻이 반대), requirements의 evidence → requirements[].sourceQuote, 정책 name → title, benefit.text → summary, benefit.maxTotal → amountMax, application의 start·end → applyStart·applyEnd. 5장 API 응답 이름은 docs/api.md를 받은 뒤 맞춘다.
- 백엔드가 물은 "공고 스냅샷 필드를 공고 담당이 채울 수 있는가"의 답: 채울 수 있다. requirements[].sourceQuote는 B-02 요건 추출의 원문 인용으로 채운다. 요건 추출은 데모 직무군 공고만 미리 하므로, 나머지 공고는 상세를 처음 열 때까지 requirements가 비어 있고 extractStatus=PENDING이다. 필드 정의(개발 명세서 v2.0 §4.4 JobRequirement)는 문서를 받아 맞춘다.

### 6.2 사용자별 B 데이터 (team07-career-mentor, PK = USER#{userId})

| SK | 내용 | TTL (expiresAt) |
| --- | --- | --- |
| PROFILE#BASIC (공통, 읽기만) | birthYear, residenceSido, residenceSigungu, residenceSince, universityRegion, graduationStatus, employmentStatus, monthlyIncome, householdIncomeLevel, desiredJobs[], desiredRegion | 없음 |
| OPP#PREFS | sort, leaveReason, leaveReasonAskedAt, notifications{email, weekly}, receivingPolicies, demoAsOf | 없음 |
| OPP#SAVED#{jobPostingId} | kind, status, snapshotId, isBusan, jobMajor, fromAlternativeOf, savedAt, scheduleNames. 비부산 공고면 GSI1PK=WATCH#{jobMajor}, GSI1SK=USER#{userId} (P1 B-12) | 없음 |
| OPP#ALERT#{policyId} | scheduledAt, scheduleName, checks | 없음 |
| OPP#NOTI#{createdAt}#{notificationId} | type, title, body, link, read, channel | 있음 |
| OPP#CAP#{yyyy-Www} | immediateCount | 2주 |
| OPP#EXPL#{jobPostingId} | 설명 문장, 사실 목록 해시 | 24시간 |
| TASK#{taskId} (공통) | 외부 공고 분석 작업(P1). taskType=EXTERNAL_POSTING_ANALYSIS | 없음 |
| IDEM#{key} (공통) | 저장 계열 POST의 Idempotency-Key. requestHash, resultId | 24시간 |

- B 아이템은 OPP# 접두어로 구분한다. 회원 탈퇴 때 USER#{userId}를 지우면 B 데이터도 같이 지워진다.
- 멱등 처리는 Powertools 멱등 유틸의 별도 테이블 대신 IDEM# 아이템 조건부 쓰기로 한다.
- 알림 ID는 SK 뒷부분({createdAt}#{notificationId})을 그대로 써서 읽음 표시 때 키를 바로 만든다.
- 공통 프로필: 생년, 거주 시·구, 학교 소재지(universityRegion), 졸업 상태, 취업 상태, 희망 직무, 소득은 PROFILE#BASIC에 있다. 10.3의 educationLevel, major, priorities는 없어서 추가를 요청한다. residenceSince는 거주 기간 조건이 있는 정책 판정에 쓴다.

### 6.4 그 밖의 저장소와 스키마 추가 요청

- S3: 팀 버킷 3개(개인 문서, KB 원천, 면접 업로드)와 용도가 달라 B 버킷 team07-opp-data-{계정 ID}를 둔다. 경로는 raw/{출처}/{날짜}/, normalized/{날짜}/, seed/, snapshots/demo-2026-11-21/, runs/{날짜}.json이다.
- S3 Vectors: 벡터 버킷 team07-opp-vectors, 인덱스 postings-v1(코사인). 키는 jobPostingId, 필터 메타데이터는 isBusan, sido, jobMajor, active, deadline(YYYYMMDD 숫자), 필터 불가 메타데이터는 title.
- team07-cache는 쓰지 않는다. 원본 응답은 S3에 두고 정규화한 값은 catalog에 넣는다.
- 공고·정책·기업 아이템은 B 수집 배치만 쓰고, 다른 파트는 읽기만 한다.
- 백엔드에 추가를 요청할 것: ① LATEST에 목록용 값, ② POSTING#{id}/ALTS 아이템, ③ PROFILE#BASIC에 educationLevel·major·priorities(2차용 talentPoolConsent는 이름만 예약), ④ catalog Streams(P1), ⑤ B용 S3 버킷과 S3 Vectors 버킷, ⑥ career-mentor GSI1에 WATCH# 값 사용(P1). 저장한 공고를 워크스페이스(WS#)와 이어야 하면 GSI2가 필요하다.

## 8. 모니터링과 유도 지표

운영 지표는 수집이 살아 있는지를, 유도 지표는 부산 쪽 선택이 늘었는지와 사용자가 불편해하는지를 본다. 둘 다 CloudWatch 대시보드 하나에 모은다.

### 8.1 운영

- 지표: 출처별 수집 건수·실패, 추출 실패율, 피드 응답 시간(p95), Bedrock·S3 Vectors 오류, 알림 발송·실패.

| 지표 | 계산 | 확인하려는 것 |

| 받음 | 공통 백엔드 | userId(Cognito sub), 공통 프로필 | 인증 컨텍스트, 프로필 읽기 | 0~2h |
| 요청 | 공통 백엔드·온보딩 | 프로필 필드 추가 (10.3) | 온보딩 폼 | 0~2h |
| 줌 | 프론트 | API 명세, 가짜 응답, 문구 규칙(4.7), 화면 목록(10.4) | mocks/ 폴더 | 0~2h |
| 줌 | 워크스페이스 담당 | PostingSaved, TargetPostingAdded 이벤트 | EventBridge 이벤트 버스 | P1 |

### 10.2 A가 받을 Posting 계약

A 명세의 DATA-04(직무별 채용 요구사항)에서 요청한 값을 B 필드에 맞춘 표다.

| A가 요청한 값 | B 필드 |
| --- | --- |
| 공고 ID | postingId |
| 기업명 | company.name |
| 직무명 | job.name |
| 필수 역량 | requirements.required |
| 우대 역량 | requirements.preferred |
| 경력·학력·자격 요건 | careerType, educationMin, requirements.certificates |
| 업무 설명 | jobDescription |
| 공고 원문 URL | sourceUrl |
| 수집·확인 시각 | collectedAt, updatedAt |

requirements의 항목마다 evidence(원문 인용)가 붙어 있어 A의 근거 검증에 그대로 쓸 수 있다.

### 10.3 공통 프로필에 필요한 값

| 필드 | 예 | 쓰는 곳 | 필수 |
| --- | --- | --- | --- |
| birthYear | 2003 | 정책 나이 판정 | 필수 |
| residence | {sido: 26, sigungu: 26290} | 정책 거주 판정, 비교 패널 | 필수 |
| school | {sido: 26, status: GRADUATING} | 지역인재 판정 | 필수 |

| employmentStatus | UNEMPLOYED, EMPLOYED, STUDENT | 정책 단계 | 필수 |

학교 소재지와 취업 상태는 B 화면에서 따로 받지 않고 공통 온보딩에 넣어 달라고 요청한다. 팀 스키마 PROFILE#BASIC의 필드 이름과 없는 값은 6.2에 있다. 온보딩에는 "부산 청년 취업·정착 지원 서비스"라는 서비스 성격을 한 줄로 알린다.

## 12. 데모 시나리오

데모는 페르소나 ①로 5분 안에 "서울 공고를 저장하는 순간 → 부산 대안 → 비교 → 목표 담기 → 알림"을 보여준다. 마지막에 통합 Agent 대화 한 번으로 같은 툴이 대화에서도 불린다는 것을 보여준다.

1. 부산 소재 대학 4학년, 데이터 분석 희망자로 로그인한다. 피드 위에 "추천순(부산 우선)" 칩이 보인다.
2. 서울 데이터 분석 공고를 저장한다. 이유 질문이 한 번 뜨고 '연봉'을 고른다.
3. 카드 아래에 "같은 일, 부산에서 2곳"이 뜬다. 하나는 지역인재 전형 대상일 수 있는 이전기관 데이터 직무, 하나는 '급여' 유형 청끌기업이다.
4. 청끌기업 공고와 나란히 비교를 연다. 급여는 서울이 높은 그대로 보이고, 주거비·지역 정책 칸이 함께 보인다. 생활비 반영 보기를 켜면 차이가 줄어드는지 보여준다.
5. 부산 공고를 목표로 담는다. 마감 D-7·D-3 일정이 생긴다.
6. 정책 지갑에서 기쁨두배통장을 "취업하면 받는 것"으로 보고, 다음 모집 알림을 신청한다.
7. 관리자 화면에서 시간을 앞당긴다. "시뮬레이션" 표시와 함께 마감 알림과 정책 열림 알림이 알림함·메일로 온다.
8. 통합 Agent에 "서울 데이터 분석 공고 보고 있는데 부산에도 비슷한 데 있어?"라고 묻는다. Agent가 BusanOpportunity 툴로 같은 대안을 사실 목록과 함께 답한다.

발표에서는 세 가지를 강조한다. 공고를 숨기지 않고 서울이 나은 칸도 보여준다. 숫자마다 출처와 기준일이 있다. CloudWatch 대시보드의 대안 클릭률·목표 전환율로 효과를 잴 수 있다.

## 13. 코드 구조와 AGENTS.md

Claude Code로 개발하므로 저장소 구조와 AGENTS.md를 먼저 만든다. 팀이 저장소 하나를 쓰면(C는 같은 저장소의 interview/ 폴더) 아래 구조를 opportunity/ 폴더로 넣고, infra/는 백엔드와 맡을 범위를 정한 뒤 둔다. AGENTS.md에는 이 명세의 규칙 중 코드가 반드시 지켜야 할 것만 옮긴다.

```text
busan-opportunity/
├── AGENTS.md
├── infra/                 # CDK(Python): 테이블, 버킷, 벡터 인덱스, Lambda, 일정, Step Functions
├── src/opportunity/
│   ├── models/            # Pydantic: Posting, Policy, Profile, SavedItem, Notification, ApiError
│   ├── config/            # opportunity_config.json
│   ├── seeds/             # 청끌기업, 이전기관, 정책 시드, 지역 통계, 지역인재 규칙, 페르소나
│   ├── ingest/            # work24.py, alio.py, youthcenter.py, normalize.py
│   ├── enrich/            # extract.py, embed.py, badges.py, regional_talent.py, precompute_alternatives.py
│   ├── core/              # ranking.py, alternatives.py, compare.py, policies.py, eligibility.py, clock.py, copy_rules.py
│   ├── api/               # rest_handler.py(APIGatewayRestResolver), agent_handler.py(BedrockAgentResolver)
│   └── notify/            # scheduler.py, notifier.py, digest.py, stream_matcher.py
├── mocks/                 # 프론트용 가짜 응답
└── tests/                 # unit/, rules/(T-01~T-22), personas/, contract/
```

AGENTS.md에 옮길 것:

- 서비스 목적 한 줄, 유도 원칙 5개, 하지 않을 것 5개 (1.3)
- 용어집: 지역인재, 이전기관, 청끌기업, 강소기업, 정책 단계, matchScore와 rankScore의 차이
- 데이터 계약: Posting, Policy, 프로필 최소 필드, SavedItem. Pydantic 모델이 기준이다
- 설정값은 opportunity_config.json에서만 읽는다. 코드에 숫자를 박지 않는다
- 툴 작성 규칙: 설명에 무엇·언제·입출력을 적는다, Pydantic 입출력, 상태는 DB에만, 문장 대신 사실 목록, 조회·저장 분리, 저장은 멱등, 오류는 원인을 구체적으로
- 날짜는 clock.py의 asOf로만 계산한다
- LLM은 core/에서 부르지 않는다. enrich/의 추출과 설명 문장에서만 부른다
- 금지: 시연 중 공공 API 실시간 호출, 인증키 하드코딩, 로그에 개인정보, 공고 숨기기
- 완료 기준: tests/rules와 tests/personas 통과
