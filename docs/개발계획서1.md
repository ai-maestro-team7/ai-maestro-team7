## 0. 이 문서만 보고 개발 시작하는 방법

1. `README_START_HERE.md`의 0~2단계 실행 → 제공된 스켈레톤의 단위 테스트 확인
2. 원본 ZIP에서 `bedrock/documents/`의 `.md` 13개 + `.metadata.json` 13개만 전용 S3 prefix에 업로드
3. 정형 CSV 3종(`selected_job_profiles`, `selected_competency_units`, `selected_qualification_links`)을 테스트 DB/로컬 인덱스로 적재
4. 프론트/백엔드 담당자와 **`userId` 발급 주체, `jobPostingId` 조회 계약, JWT 인증 방식, API 경로** 합의
5. PDF·텍스트 입력 → CareerProfile 생성 → 직무 적합도 → 첨삭 → 학습 경로 순서로 연결
6. Agent 도구는 위 API들을 재사용하고, 고정 분석 파이프라인의 필수 검증·저장 순서를 우회하지 않도록 구현
7. `validation/sample_queries.jsonl`과 `validation/agent_prompt_tests.jsonl`로 정확성·안전성 자동 점검

**구현 기준:** 단일 직무 데모에 국한하지 않음. ZIP에 이미 존재하는 8개 직군/11개 NCS 직무의 직무 설명 검색을 지원. 특정 회사·공고의 필수 요건은 반드시 공고 원문을 우선함.

**한계:** 이 명세서의 API 경로·DB 키·가중치는 팀에서 선택할 **제안 계약**임. 아직 AWS 배포와 실데이터 연동이 완료됐다고 주장하지 않음.

### 1.1 MVP 수용 기준

- 텍스트 또는 PDF로 등록한 이력서가 구조화되고 **원문 근거**가 연결됨
- 특정 공고를 선택하면 **공고 요구사항 우선**의 직무 적합도·격차 설명 제공
- 첨삭이 원문 구절/경험 블록과 연결되고 허위 경험·수치를 추가하지 않음
- NCS 학습자료와 공식 자격 연결표를 이용한 학습 로드맵 생성
- 사용자 A가 사용자 B 자료를 조회할 수 없고, 예외/재시도/삭제 동작이 테스트됨
- 공식 자료 검색 결과에 문서 ID, 출처 URL, 기준일이 첨부됨
- AWS 장애·AI 유효성 오류가 로그·지표로 관측되며 알림 경로가 존재함

### 1.2 상태 표시 규칙

- **패키지에서 준비됨**: 파일이 ZIP에 존재함. AWS 배포 완료를 의미하지 않음
- **API 승인/신청**: 공유된 팀 신청 내역 또는 패키지 문서의 기술. 실호출 결과 아님
- **개발 필요**: 코드/테이블/배포/프론트 연결 아직 미구현
- **검증 필요**: AWS 리전·쿼터·키 접근·법적 이용조건·공고 필드 제공 여부 등을 직접 확인해야 함

### 2.1 RAG 문서와 정형 데이터의 구분

1. **KB 검색용**: 직무 정의, 능력단위·학습 목표, 팀 작성 상담/공정채용 지침
2. **정형 계산용**: NCS 코드, 자격 연결, 훈련 시간, 지원 필수·우대조건, 점수 규칙
3. **외부 API/짧은 캐시용**: 채용공고, 교육 개강/모집 상태, 시험 일정, 정책 접수 기간
4. **개인정보 전용 저장소**: 이력서·자소서·Story Bank·프로필·대화 — 공용 KB 금지
5. **비공개 평가셋**: 골든 이력서·정답 라벨·프롬프트 공격 테스트 — KB에 색인 금지

### 2.2 원본 데이터에서 주의할 점

- `selected_qualification_links.csv`에는 동일 자격/능력단위의 중복 관계가 존재할 수 있으므로 `(competency_unit_code, qualification_code, unit_type)`로 후보 중복 제거. 훈련시간이 다른 레코드의 값은 임의 합산 금지
- 원본 `raw/` CSV 인코딩 일부가 CP949. 초기 로더에서는 `structured/`의 UTF-8 정규화 버전 우선
- `ncs_competency_training_info`의 `training_hours`는 공식 훈련 정보이지 **개인의 자격증 취득 소요 기간**이 아님
- NCS–자격 연계표의 `필수/선택`은 해당 **능력단위–과정평가형 자격 연결 내 구분**이고, 개별 채용공고의 필수/우대조건을 의미하지 않음
- 국가자격 CBT 과목 사전 데이터는 종목 연결키가 없으므로 특정 자격증의 과목이라고 자동 조인 금지
- `raw/fair-hiring/`의 PDF/HWP 원본은 개별 재이용 허용이 확정되지 않아 공용 KB에 직접 업로드하지 않음
- NCS 학습모듈 원문 PDF는 ZIP에 **포함되지 않음**. 공식 링크·훈련목표 색인을 활용하며 원문 재배포는 별도 라이선스 확인 필요
- NCS 최신 기준정보 API, 고용24 표준직무기술서 API, 채용·훈련 API의 최신 응답은 패키지 자체에 **미포함**. 팀 승인 범위 안에서 런타임 연동/수집

## 3. 전체 아키텍처와 정보 흐름

```
[Frontend / 공고별 워크스페이스]
       │ Bearer JWT, docId / jobPostingId / workspaceId
       ▼
[팀 API Gateway 또는 공통 Backend]
       │ userId는 JWT에서만 확정, 요청 본문 userId는 신뢰하지 않음
       ▼
[멘토링 API Lambda]
       ├── upload-url → 개인 S3 bucket, presigned PUT
       ├── complete → HeadObject 검사, 작업 상태 생성 → SQS
       ├── analyses / reviews / learning-paths → SQS 비동기 작업
       ├── profiles / stories / results → DynamoDB 사용자 소유권 검사
       └── agent/chat → Bedrock Agent / action-group
                          │
[SQS + DLQ] → [worker Lambda / Step Functions]
       ├── 문서 텍스트 추출: PDF 텍스트 레이어 → 부족할 때 Textract OCR
       ├── Bedrock 역량 구조화 → JSON Schema + 원문 근거 검증
       ├── 공통 채용 DB에서 공고 스냅샷 조회
       ├── Bedrock KB Retrieve (NCS/공정채용/학습)
       ├── Lambda 정형 역량 매칭·필수조건 검증
       ├── Bedrock 첨삭 또는 로드맵 설명
       ├── 외부 고용24·자격 API: 최신 개강·접수·시험일 확인
       └── DynamoDB + 비공개 S3에 결과 저장
                          │
[CloudWatch custom metrics + Alarms] → [SNS 운영자 알림]
```

**권장 주요 기술**: Python 3.12+, boto3, Pydantic v2, pytest, AWS Lambda, S3, DynamoDB, SQS/DLQ, API Gateway, Bedrock, Knowledge Bases, Guardrails, CloudWatch, SNS. Bedrock Agent는 사용자 대화 흐름의 도구 라우터로 사용. RAG 벡터 저장소는 AWS 리전/쿼터/가격 확인 후 S3 Vectors 또는 팀 공통 OpenSearch 중 선택.

### 3.1 중요 기술 결정

- **Textract 한국어**: 2026년 11월 확장된 언어 지원에 한국어가 포함됨. `DetectDocumentText`/비동기 탐지 계열 지원 확인 필요. 스캔 OCR 품질은 샘플 문서로 검증. **디지털 PDF의 텍스트 레이어가 정상 추출되면 파서 우선**, 스캔 PDF는 Textract 사용
- **Guardrails 한국어**: Standard tier에서는 한국어 콘텐츠 필터·근거 검사 지원. 다만 실제 리전/모델/티어에 따라 달라질 수 있으므로 검증 필수. Guardrails만으로 사실 검증 완료로 간주하지 않음
- **S3 Vectors**: 의미 검색만 제공하고 hybrid search는 미지원. 자격증 코드·NCS 코드는 정형 필터로 정확 조회. 커스텀 메타데이터 용량 제한이 있으므로 문서 메타데이터가 허용 크기 이내인지 점검
- **Agent vs 고정 파이프라인**: `POST /analyses` 등 필수 기능은 고정 워크플로와 코드 검증이 완수. Agent는 사용자 의도를 해석해 이미 구현된 기능/조회 도구를 호출할 뿐 핵심 저장/검증을 생략할 수 없음
- **서류 점수 vs 합격률**: 0~100 점수는 `DOCUMENT_BASED_MATCH`로만 표시, 실제 합격 확률·서류 합격 9칸 예측과 혼동하지 않음

| `profileId`, `profileVersion` | string, int | 멘토링 | 수정 시 버전 증가 |
| `storyId` | string | Story Bank | 여러 문서에서 재사용 |
| `analysisId` | string | 멘토링 | 당시 프로필/공고 스냅샷 고정 |
| `jobPostingId` | string | 팀 채용 API | 팀 합의 필수 |
| `jobSnapshotVersion` | string | 팀 채용 API | 공고 변경 시 재분석 구분 |
| `workspaceId` | string | 팀 워크스페이스 | 공고 세션 식별 |
| `reviewId`, `reviewVersion` | string, int | 멘토링 | 첨삭 결과 불변 저장 |
| `learningPathId` | string | 멘토링 | 출처·기준일과 함께 |
| `requestId`, `idempotencyKey` | string | API / 프론트 | 재시도 중복 방지 |

모든 엔티티에 `schemaVersion`, `createdAt`, `updatedAt`, `ownerUserId`, `sourceSnapshotId`, `modelId`, `promptVersion`, `status`를 필요한 범위에서 보관.

### 4.2 증거·역량 상태 (정규화)

`factStatus`: `VERIFIED`(사용자가 증빙 내용을 확인), `NEEDS_CONFIRMATION`, `SUGGESTION`(모델 제안); `evidenceLevel`: `EVIDENCED`(수행 행동/산출물 근거), `PARTIAL`(부분 근거), `SELF_REPORTED`(보유 선언만 있음), `NOT_FOUND`(서류에 미기재), `USER_CONFIRMED_GAP`(사용자가 미보유/부족을 확인).

> **`NOT_FOUND` ≠ 실력 없음**. 격차 추천을 하기 전에 추가 질문·증거 보완을 먼저 제안함. 자기소개서에 사용할 수 있는 사실은 `VERIFIED` 및 원문 확인이 가능한 정보로 제한.
>

## 5. 기능별 상세 개발 명세

### F-01 문서 업로드·텍스트 추출·역량 프로필

**입력:** 사용자 직접 입력 텍스트(1,000~30,000자 예시 정책) 또는 PDF(정책상 10MB/20페이지 제한 예시), `documentType=RESUME/COVER_LETTER/CAREER_HISTORY/PORTFOLIO`, `workspaceId?`. 제한 값은 팀/계정 쿼터에 맞춰 설정 가능하게 환경변수로 분리.

**처리 단계**

1. 요청 JWT 확인 → `ownerUserId` 확정 → 업로드 허용 확장자·크기 검사
2. `POST /documents/upload-url`: 문서 메타데이터 PENDING 저장, 개인 S3 prefix에 PUT presigned URL 발급(짧은 TTL), content-type/checksum 조건
3. 프론트가 S3에 파일 업로드 → `POST /documents/{id}/complete`: HeadObject·크기·소유권·checksum 검사, 중복 complete는 멱등 처리
4. SQS에 `DocumentExtractionRequested` 메시지 전송, HTTP 202 반환
5. Worker가 PDF 텍스트 레이어 추출 → 텍스트가 부족/깨짐이면 Textract 처리. 스캔/다중 페이지는 비동기 Textract Start→Get + NextToken, 페이지·원문 구간 저장
6. 텍스트 추출 품질 검사(공백/문자 비율, 페이지별 길이, 인코딩), 이용자에게 확인·수정 화면 제공
7. 개인정보/민감정보는 모델 입력의 불필요한 부분에서 마스킹(이름·연락처·주민번호·주소 등), 원문은 개인 S3에 격리
8. Bedrock에 구조화된 역량 추출 요청(고정 JSON 스키마), 프로젝트·경력·자격·기간·수치 등 원문 근거 인용
9. Pydantic 검사 → 근거 문구가 원문에 존재하는지 확인 → 모델 결과가 모호한 필드 `NEEDS_CONFIRMATION`
10. 불필요한 경력·수치 생성 등 심각한 허위 사실 발견 시 자동 수정 요청 1회, 이후 `REQUIRES_USER_REVIEW`로 종료
11. CareerProfile v1 저장 후, 사용자 확인 시 Verified revision v2 생성(기존 v1 보존)
12. 분석 완료 이벤트 발행: `career.profile.completed`

**상태 전이**

`UPLOADED → EXTRACTING → EXTRACTED → ANALYZING → REQUIRES_USER_REVIEW → COMPLETED` 또는 각 단계에서 `FAILED`. 단, 텍스트 직접 입력은 EXTRACTING 생략 가능. 결과 완료 전 조회는 `202 PENDING/PROCESSING`.

**필수 입력 누락/에러**

- PDF가 손상됐거나 암호화됨 → `422 DOCUMENT_UNREADABLE`
- 텍스트 추출량 부족 → `REQUIRES_USER_REVIEW` + 사용자가 직접 텍스트 추가 입력
- 권한 없는 `documentId` → `404` 또는 `403`(팀 정책에 통일; 정보 노출 우려 있으면 404)
- Textract 타임아웃 → 재시도 가능한 `FAILED`와 문서 직접 입력 폴백
- 경력·성과 없는 이력서 → 빈 리스트 유지(가상 경험 생성 금지)
- 중복 요청 → 동일 idempotency key면 기존 `documentId`/결과 반환

**완료 기준**

- 사용자 A PDF/텍스트 2형태 모두 처리
- `skills[].evidenceIds`가 실제 문서 원문에 매핑
- 한국어 스캔 이력서 샘플 테스트
- 사용자 확인/수정 후 프로필 버전 증가
- 다른 사용자의 문서 조회/업데이트 차단

### F-01B Story Bank(경험 블록) 발굴 및 검증

**목적:** 프로젝트·아르바이트·동아리·학업 경험을 간단히 설명하면 1~3개의 사실 확인 질문을 단계적으로 생성, `Situation/Task/Action/Result/Learning` 구조로 저장.

**입력:** `rawExperience`, `targetRole?`, `sourceDocumentId?`, `existingStoryId?`.

**처리**

1. 사용자 원문을 별도 StoryDraft 저장
2. 경험의 주체, 사용자 행동/팀 성과, 기간, 숫자 측정 기준 구분
3. 부족한 STAR 요소를 확인 질문 최대 3개로 제시
4. 답변을 버전으로 추가하고 다른 사용자 경험과 절대 혼용하지 않음
5. `verifiedFields`는 사용자가 확인한 필드만 기록, 미확인 사실은 `NEEDS_CONFIRMATION`
6. 직무/자소서 문항과 연결할 경험 ID만 반환하여 F-03에서 재사용
7. 삭제 시 문서·첨삭 연관 참조 정책에 따라 개인 원본 삭제 및 인덱스 제거

**StoryItem 예시**

```
{
  "storyId":"story-demo",
  "status":"DRAFT",
  "title":"대학 팀 프로젝트",
  "situation":"학교 팀 프로젝트 진행",
  "task":null,
  "actions":[],
  "result":null,
  "learning":null,
  "competencyCandidates":[],
  "questions":["프로젝트에서 직접 맡은 업무는 무엇이었나요?"],
  "confirmedFields":["situation"],
  "version":1
}
```

`DRAFT` 상태의 내용으로 완성된 STAR 성과나 KPI 생성 금지.

### F-02 직무 적합도·지원자격 진단

**입력:** `profileId`, `profileVersion`, `jobPostingId?`, `targetNcsCode?`. 최소 하나의 직무/공고 식별자 필요.

**처리**

1. 권한 검증 후 CareerProfile 최신 또는 지정 버전 조회
2. `jobPostingId`가 있으면 공통 채용 API에서 공고 요구사항·근무지·마감·직무기술서 조회
3. `jobPostingId`가 없으면 `selected_job_profiles`에서 NCS 표준 직무 정의 조회
4. 직무명-코드 매핑이 모호하면 후보 NCS 2~3개 반환하고 사용자 확인
5. NCS 직무별 능력단위 135개 중 해당 NCS 코드와 일치하는 항목 필터링
6. Bedrock KB에서 관련 설명(메타데이터 `ncs_code` 또는 `job_role`) 검색
7. 요구사항마다 사용자 증거 스팬과 연결, 근거 상태(EVIDENCED/PARTIAL/SELF_REPORTED/NOT_FOUND/USER_CONFIRMED_GAP) 분류
8. 자격·경력·학력 등 공고의 **명시적 필수 자격조건**은 결정적 규칙으로 `ELIGIBLE/INELIGIBLE/NEEDS_VERIFICATION` 판정
9. 점수는 코드에서만 산출, `scorePolicyVersion` 기록
10. Bedrock으로 요약과 다음 질문 생성(정량 점수·요건의 임의 변경 금지)
11. 결과·공고 스냅샷·근거·기준일 저장

**권장 참고점수 계산** (v1의 70/20/10 제안 유지, 새로 추가한 '미확인 구간' 보완):

- 분류별 가중치: 필수 역량 0.7, 우대 역량 0.2, 관련 경험 근거 0.1
- `EVIDENCED=1.0`, `PARTIAL=0.5`, `SELF_REPORTED=0.25`, `NOT_FOUND=0`(하한), `USER_CONFIRMED_GAP=0`
- `NOT_FOUND`에만 상한값 `1.0`을 부여해 미확인의 **가능 범위** 표시. `USER_CONFIRMED_GAP=0`으로 유지
- 각각 요구사항의 `weight`로 가중평균, 범주가 공백이면 남은 범주의 비중으로 재정규화
- 최종 `fitScore = round(100 × weighted lower)` 및 `potentialUpperBound = round(100 × weighted upper)`
- `fitScore`는 **서류에 나타난 근거 기반 일치도 하한**, `potentialUpperBound`는 **추가 증빙 가능성을 고려한 범위 상한**이지 확률이 아님
- 요구사항이 0개라면 점수 `null`, 상태 `INSUFFICIENT_REQUIREMENTS`
- `eligibilityStatus=INELIGIBLE`이면 기술 적합도가 높더라도 '지원 조건 미충족'을 최우선 표시

**정책 예시**: 필수 2개(근거 있음 1, 미확인 1), 우대 1개(자기보고), 경험 근거 1개(근거 있음)인 경우 `fitScore`와 상한을 함께 표시. 실제 채용 합격 확률로 변환하지 않음.

**완료 기준**

- 동일 입력 → 동일 점수(결정적), 100번 반복 테스트
- 요구사항 0건/모호한 NCS/지원자격 미확인/공고 종료 상황 처리
- 출처 정보와 검사 기준일 필수
- 점수·합격 가능성을 혼동하는 자연어 출력 차단

### F-03 자기소개서·이력서 첨삭

**입력:** `documentId` 또는 `inputText`, `documentType`, `jobPostingId?`, `workspaceId?`, `profileId?`, `questionText?`, `maxCharacters?`, `storyIds?`.

**처리**

1. 개인 원문/선택 공고 스냅샷/사용자 확인된 경험 블록 로드
2. 기업 인재상은 공식 확인된 자료가 있을 때만 포함. 출처가 없으면 공고 직무 요구사항만 사용
3. 자기소개서 문항 의도 분류(지원동기/직무경험/협업/갈등/문제해결/성장 등)
4. 관련 Story Bank 항목 후보 선택, 경험의 `VERIFIED`/`NEEDS_CONFIRMATION` 분리
5. 서류 분석 기준: 직무 관련성, 행동·성과 구체성, 본인 역할, 문장 논리, 사실 일관성, 블라인드 채용 관련 조건
6. Bedrock 구조화 출력: `originalSpan`/`issueType`/`reason`/`improvementAction`/`revisedExample`/`needsUserConfirmation`
7. 수정 예시에 포함된 숫자, 자격, 직위, 수상, 회사·프로젝트명, 성과가 원문·검증된 경험과 일치하는지 후처리
8. 없는 사실이 필요한 경우 **문장 생성 대신 구체적 확인 질문** 제공
9. 제한 글자수/바이트 기준은 프론트와 통일(UTF-8 byte vs 글자수 구분) 및 별도 코드 계산
10. 첨삭 결과는 수정 문서 자체가 아니라 '제안'으로 저장. 사용자 수락·저장 시 새 DocumentVersion 생성
11. 사용한 `storyId`, `sourceJobSnapshotId`, `promptVersion`과 검증 상태 기록

**수정 결과 단위**

```
{
  "reviewId":"review-demo",
  "overallFeedback":"역할 설명은 있지만 직접 수행한 행동이 구체적이지 않습니다",
  "issues":[{
    "sourceSpan":{"startChar":0,"endChar":22},
    "issueType":"MISSING_ACTION",
    "reason":"사용자가 실제로 수행한 행동 확인 필요",
    "improvementAction":"직접 수행한 구체적 작업을 추가",
    "revisedExample":null,
    "needsUserConfirmation":true,
    "questions":["본인이 맡은 구체적 작업은 무엇인가요?"]
  }],
  "factCheckStatus":"NEEDS_CONFIRMATION"
}
```

위 예시는 스키마 설명용 시연 데이터로 실제 사용자 이력이 아님.

**실패 및 예외**

- 공고 미제공 → NCS 기준 일반 첨삭, 기업 맞춤 첨삭임을 주장하지 않음
- 최신 기업 인재상 출처 없음 → 인재상 비교 제외
- 자소서 빈 텍스트 또는 대상 문항 없음 → 400 또는 `missingInputs` 반환(팀 UX 규칙)
- 원문 스팬 매핑 불일치 → 검증 실패/후속 수정, 무조건 저장 금지
- 비공개·차별 가능 개인정보가 평가 요건으로 사용되면 제외(단, 채용공고의 법정 자격·지역인재 적용은 별도 공고 검증)
- 블라인드 공채 → 공고 기준에 맞게 비식별화 경고

### F-04 역량 격차 분석

**입력:** `analysisId` 또는 `profileId + targetJob`; F-02 계산을 재사용하며 별도로 추측하지 않음.

**4가지 분류**

| 분류 | 결정 조건 | 권장 다음 행동 |
| --- | --- | --- |
| 확인된 강점 | 명시적 행동/산출물 근거 있음 | 자소서·면접 소재 강조 |
| 부분 증거/증빙 부족 | 관련 행동 있으나 깊이·결과 확인 어려움, 자기보고 | 사례·프로젝트 증빙 보완 |
| 미확인 | 입력 자료에 없음/공고 직무 모호 | 사용자 사실 확인 질문 |
| 확인된 격차 | 사용자가 미보유를 확인했거나 객관적 필수 자격 부족이 확인됨 | 실습/자격/교육 추천 |

**우선순위 규칙(제안):** 실제 공고의 필수 요건 > 해당 공고의 우대요건 > 관련 NCS 학습 목표; 확인된 격차만 '학습 필수'로 표시. `NOT_FOUND`는 별도 `verificationTasks`로 우선 질문.

**완료 기준:** F-02 점수·요건·분류와 항상 일관. 질문/학습 과제를 구분하고 같은 항목이 중복 추천되지 않음.

### F-05 학습·자격·지역 교육 경로 추천

**입력:** `analysisId`, `weeklyStudyHours(1~40)`, `preferredFormat=ONLINE/OFFLINE/HYBRID`, `targetDate?`, `location=BUSAN`, `budgetLimit?`, `startDate?`.

**처리**

1. F-04에서 확인된 격차와 우선 확인해야 할 미확인 사항 분리
2. `selected_competency_units.csv`로 관련 능력단위·학습목표·`training_hours` 조회
3. `selected_qualification_links.csv`에서 공식 연결 자격 후보 생성 + 관계 중복 제거
4. `national_qualifications_authorities`로 자격 실재 여부·시행 기관 확인
5. Knowledge Base에서 해당 직무의 NCS 설명·팀 작성 학습 방법론 검색
6. 목표일까지 남은 기간과 주간 가능 시간을 계산(최소 실행 가능한 과제부터 설계)
7. Bedrock으로 목표 → 짧은 실습 → 산출물 → 심화 학습 순서의 주별 로드맵 생성
8. 팀이 확보한 고용24 훈련 API에서 **실제 모집 중인** 지역/온라인 과정 검색, 공식 링크·조회 시각 첨부
9. 자격 시험 API로 접수일/시험일/합격 발표일 검증. 제공되지 않으면 `SCHEDULE_UNVERIFIED`
10. 부산 청년지원 프로그램은 팀이 검증한 정책 DB에서 조회. 접근 불가 시 공식 안내 링크만 제공
11. 학습 완료 체크박스/수정 기록 저장, 업데이트 시 RoadmapVersion 증가

**일정 추천 규칙**

- 자격증이 공식 NCS와 연결됐다고 해당 기업의 필수 자격은 아님
- **훈련시간 ≠ 실제 학습 기간**. 훈련시간을 참고 정보로 제시하고, 주간 학습 가능 시간/기초 수준을 고려해 *추정 기간* 표시
- `시험일 < 채용 마감일`만으로 '지원 가능'이라고 판단하지 않음. 자격 **합격 발표일/발급 가능일 및 공고의 자격 인정 기준일**을 함께 확인
- 시험일정 미확인 시 날짜·회차·마감 '생성' 금지
- 지역 교육과정 0건이면 일반 실습 계획만 제공 + `NO_LIVE_COURSES`
- 희망 직무 미설정 시 진로 탐색/질문 단계로 분기

**완료 기준**

- 선택된 모든 교육/자격 항목에 `officialUrl`, `checkedAt`, `verificationStatus` 존재
- 교육·시험 API 장애 시 전체 로드맵을 실패시키지 않고 `PARTIAL_SUCCESS` 반환
- 사용자 주간 학습시간과 로드맵 총 학습시간 일관성 검증

### F-06 통합 Agent·대화와 공고 세션

**구성:** `CareerMentoringAgent` 단일 Agent + Action Group(또는 팀 내부 호출용 Lambda). 원본 ZIP의 프롬프트는 `agent/CAREER_MENTOR_AGENT_PROMPT.md`를 상위 지침으로, `prompts/00_PROMPT_ROUTER.md`에서 한 번에 하나의 `primary_intent`, 선택한 `01~07` 프롬프트 한 개만 적용.

| --- | --- | --- | --- |

- 확인 불가 직무 정보에는 `UNVERIFIED` 표시
- 사용자가 허락하지 않은 개인정보 공개·외부 API 전송 금지
- Agent가 다른 사용자 프로필을 액세스하려 하면 도구 레이어에서 403/404
- Agent 장애 시 각 기능의 고정 REST API는 독립 동작

### F-08 모니터링·알림·보안 운영

**구조화 로그(개인정보·키 제외)**: `timestamp`, `requestId`, `userIdHash(optional)`, `jobId`, `feature`, `status`, `durationMs`, `modelId`, `promptVersion`, `kbDocumentIds`, `validationOutcome`, `errorCode`, `retryCount`. 원문 PDF/자소서/상세 개인정보 및 인증키가 포함된 전체 URL은 절대 출력하지 않음.

**CloudWatch 커스텀 메트릭**: `DocumentParseFailure`, `EvidenceValidationFailure`, `LLMSchemaFailure`, `GroundingFailure`, `KBNoHit`, `InvalidQualification`, `StaleCourseData`, `AnalysisLatency`, `SqsDlqMessages`, `BedrockThrottling`, `InvocationCostEstimate`.

**권장 임계값(초기 제안)**:

- Lambda 오류 5분 3회 이상
- Bedrock 오류 5분 3회 이상
- 최근 20건 중 AI 검증 오류 5건 이상
- SQS DLQ 메시지 1개 이상
- API 데이터 최신성 임계 초과 1회 이상
- AWS Budget 금액 기준 50/80/100% 알림

**알림 메시지**: "feature=review, requestId=..., errorCode=SCHEMA_INVALID, lastSeen=..." 등 비식별 메타데이터만. 사용자 서류 문구·API 키 포함 금지.

**보안 필수**

- S3 비공개, Block Public Access, 서버측 암호화, 짧은 presigned URL
- API는 JWT 서명·audience·issuer 검증, 사용자별 소유권 체크
- DynamoDB 파티션 키는 `USER#{userId}`로 사용자 분리, 다른 사용자 쿼리 불가능하게 서비스 계층 검증
- Secrets Manager 키를 런타임 로드, Git/env/로그에 실키 저장 금지
- API 요청에 ID 외의 사용자 지정 S3 key를 받지 않음. 서버가 생성한 key만 사용
- 개인 이력서를 공용 KB에 색인하거나 타 사용자 추천 근거로 사용 금지
- 데이터 보관기간·삭제정책을 팀 개인정보 정책에 맞게 설정, 삭제 시 S3 원문+추출본+프로필+파생 분석+캐시까지 추적
- 공고/기업 문서는 프롬프트 인젝션 가능한 외부 입력으로 분류

## 6. REST API 계약 상세 (`/api/v1/mentoring`)

**공통 정책**

- Auth: `Authorization: Bearer <JWT>`; `userId`는 본문에 받지 않고 JWT claim에서 결정
- Idempotency: 생성형 POST는 `Idempotency-Key` 헤더 지원 권장(동일 사용자+body hash+키)
- `Content-Type: application/json`; 파일 전송은 **presigned S3 PUT**
- 비동기 작업 생성 → 202 + `taskId`/리소스 ID/`status=PENDING`; 결과는 GET polling
- `status` 공통: `PENDING`, `PROCESSING`, `REQUIRES_USER_REVIEW`, `PARTIAL_SUCCESS`, `COMPLETED`, `FAILED`
- 공통 응답 메타: `requestId`, `createdAt`, `schemaVersion` 및 상황별 `sourceCheckedAt`
- 상세 명세: 동봉 `openapi.yaml`을 프론트·공통 BE 계약 초안으로 사용

## 7. DynamoDB 및 S3 설계

### 7.1 권장 MVP 테이블 (서비스별 여러 테이블보다 공통 테이블 + 타입 분리)

테이블 `CareerMentor`:

- PK(string) `PK`, SK(string) `SK`
- GSI1 PK `GSI1PK`, SK `GSI1SK` (작업 상태 또는 workspace 관련 조회)
- TTL `expiresAt`는 **임시 업로드/멱등 키에만**. 사용자의 문서나 중요한 분석의 TTL 자동 삭제 금지

| 엔티티 | PK | SK | 대표 필드 |
| --- | --- | --- | --- |
| Documents | `USER#id` | `DOC#documentId` | type, s3Key, extractionStatus, extractedTextKey |
| CareerProfile | `USER#id` | `PROFILE#profileId#V#0001` | skills, evidenceRefs, documentIds |
| ProfileLatest | `USER#id` | `PROFILE#LATEST` | latestProfileId, version |
| StoryBank | `USER#id` | `STORY#storyId#V#0001` | STAR, confirmedFields |
| StoryLatest | `USER#id` | `STORY#storyId#LATEST` | version |
| JobAnalyses | `USER#id` | `ANALYSIS#analysisId` | profileVersion, snapshotId, score, gaps |
| DocumentReviews | `USER#id` | `REVIEW#reviewId` | sourceDocVersion, issues, promptVersion |
| LearningPaths | `USER#id` | `PATH#learningPathId` | roadmap, qualifications, courses |
| Jobs/Metadata | **공통 채용 DB 소유** | — | jobPostingId, snapshots |
| Idempotency | `USER#id` | `IDEMPOTENCY#key` | requestHash, resultId, expiresAt |
| EvaluationLogs | 별도 운영 로그 테이블 또는 CloudWatch | — | 최소한의 비식별 검증 메타 |

긴 문서 텍스트/첨삭 전문은 DynamoDB 400KB 아이템 상한을 고려해 S3 private object에 보관, DB에는 `s3Key`, `checksum`, `size`와 메타만.

**인덱스 패턴**

- `GetItem(PK=USER#jwt.sub, SK=DOC#...)` → 소유권 자동 결합
- 사용자 경험 목록은 `begins_with(SK,'STORY#')`, latest 기록 분리
- `workspaceId` 기반 결과 목록은 GSI1 `GSI1PK=WORKSPACE#workspaceId` 단, 조회 후 **ownerUserId** 재확인 필수
- 대량 검색/집계는 별도 인덱스 설계; MVP에서 Scan 사용 금지

### 7.3 데이터 정규화·조인·분석 스냅샷

- NCS 정규화 key: `ncs_subcategory_code`
- 능력단위: `competency_unit_code` + `source_reference_date`
- 자격 연결: `(competency_unit_code, qualification_code)`의 관계 후보
- 공고: 팀 공통 `jobPostingId` + `snapshotId` (공고 업데이트 후 이전 분석 근거 추적)
- 이력서: `profileId + profileVersion` (프로필 수정 후 이전 분석 결과 변하지 않음)
- 첨삭: `documentId + sourceDocumentVersion` (수정 전후 비교/재현 가능)

## 8. RAG 데이터 적재 및 검색 구현

### 8.1 AWS 콘솔 구축 순서

1. 확정 리전에서 Bedrock LLM/한국어 임베딩 모델/Guardrails/Textract 권한 확인
2. private S3와 **분리된 KB source S3** 생성
3. ZIP `bedrock/documents/`만 추출; `.md`와 짝이 맞는 `.md.metadata.json` 13쌍 확인
4. KB source bucket의 `docs/` prefix에 두 파일을 함께 업로드
5. Bedrock Knowledge Bases → S3 데이터 소스 → 위 prefix 지정
6. 벡터 스토어는 S3 Vectors 또는 팀 공통 벡터 스토어 선택; 문서 메타데이터 크기·필터 확인
7. 임베딩 모델 선택 후 Data Sync 실행 → 성공 로그 및 ingestion job ID 기록
8. `Retrieve` API로 `validation/sample_queries.jsonl` 25건 질의
9. `metadata`로 `job_role`/`ncs_code`/`document_type` 필터 검증
10. 실패 쿼리는 chunk 전략/메타데이터와 문서 구성을 수정해 재동기화

### 8.2 검색 질의 계약

**Retrieve 입력(의미상 예시)**:

```
{
  "query":"인사 직무에 필요한 능력단위와 학습 목표",
  "filters":{"job_role":"인사","document_type":"ncs_job_profile"},
  "topK":5
}
```

구체적인 boto3 요청 타입은 `bedrock-agent-runtime.retrieve` API에 맞게 어댑터 함수가 변환.

**내부 KnowledgeCitation 구조**:

```
{
  "documentId":"job_profile_02020201_인사",
  "title":"인사",
  "sourceUrl":"https://www.data.go.kr/data/15175388/fileData.do",
  "ncsCode":"02020201",
  "chunkText":"<검색에서 받은 실제 텍스트>",
  "retrievalScore":0.81,
  "sourceReferenceDate":"2026-04-27",
  "retrievedAt":"<ISO UTC>"
}
```

`retrievalScore`는 검색기 수치이지 사실 신뢰도·합격률이 아님. 샘플은 필드 설명용. 실제 응답에는 `retrievedAt`과 출처를 반환.

### 8.3 직무 모호성·근거 부족 대비

- NCS 코드가 정해졌으면 사전 분류 CSV에서 정확한 `ncs_subcategory_code` 우선 조인
- 후보가 여러 개이면 한 개를 고정 확정하지 말고 `ncsCandidates[]` 반환
- KB 결과 0건이면 `NO_EVIDENCE`, 해당 분야 일반론에 근거 없는 기업별 필수조건을 생성하지 않음
- `KB`의 팀 작성 상담 방법론은 **작성 방식 근거**이지 NCS 직무 필수능력의 공식 출처가 아님
- `raw/` 8개 공정채용 PDF/HWP와 외부 공고 첨부는 재배포 조건 재확인 전 색인 금지
- 최신 API를 도입할 때 `dataset_catalog.csv`와 같은 메타데이터로 원본 버전·수집일·해시 기록

## 10. 비동기 작업·이벤트·재시도 설계

### 10.1 작업 큐 메시지

```
{
  "eventType":"career.document.extract.requested",
  "schemaVersion":"1.0",
  "taskId":"task-demo-001",
  "ownerUserId":"<internal user id, never logged>",
  "resourceId":"doc-demo-001",
  "documentVersion":1,
  "idempotencyKey":"idem-demo-001",
  "createdAt":"2026-11-20T00:00:00Z"
}
```

다른 작업 유형: `career.profile.extract.requested`, `career.jobfit.requested`, `career.review.requested`, `career.learning.requested`. SQS에는 원문 이력서·자소서·키를 넣지 않고 리소스 ID만 전송. Worker가 내부 저장소에서 개인 데이터 읽을 때 다시 소유권을 검증.

### 10.2 큐·상태 전이·중복 메시지

- SQS **at-least-once** 전송을 고려해 Consumer 멱등 처리
- 상태 업데이트에 DynamoDB conditional write로 진행 중/완료 중복 처리 방지
- Bedrock 429/일시 5xx → exponential backoff+jitter, 설정된 횟수 초과 시 DLQ
- 잘못된 입력·근거 불일치 → 무조건 반복 재시도하지 않고 검증 상태 반환
- Textract 긴 작업 → StartDocumentTextDetection 후 비동기 완료 확인, NextToken으로 모든 페이지 획득
- Step Functions 사용 시 필수 순서 `Extract → Validate → Profile → Retrieve → Calculate → Save` 고정
- 작업 성공 후 이벤트 알림은 상태가 DB에 확정 저장된 뒤 발행(중복 알림은 outbox/idempotency 검토)

### 10.3 로컬 개발에서 사용하는 폴백

- Bedrock 미연결: `MockLLM`으로 JSON fixture를 반환해 API/상태/권한 흐름 테스트
- KB 미연결: `selected_job_profiles.csv`와 `selected_competency_units.csv` 기반 로컬 검색
- 고용24 API 미연결: 자격/훈련 목록은 빈 배열 + `NOT_CONNECTED`, 가짜 현재 모집 과정 금지
- 팀 채용 API 미연결: 공식 공고인 척하지 않는 별도의 `sourceType=DEMO` 샘플 데이터

```
  "verificationQuestions":["노무 업무 경험이 있나요?"],
  "fitAnalysisId":"analysis-demo-001",
  "allowRawResume":false
}
```

모의면접에서 AI가 생성한 잘못된 평가를 CareerProfile의 **확인된 보유 역량으로 자동 반영하지 않음**.

### 12.3 채용 공고 담당자에게 요청할 계약

- `GET /internal/job-postings/{jobPostingId}` : 공고 스냅샷 + 직무·필수/우대·자격·학력·경력·근무지·마감일·원문 링크
- `jobPostingId`, `snapshotId`, `requirements[].sourceQuote`, `isExpired`, `sourceCheckedAt` 필수
- 공고 내용이 구조화되지 않으면 원문 `rawDescription` 함께 반환(허용된 범위 내)
- 공고 전문 재배포 조건이 제한되는 경우 원문 링크 + 허용 필드만 저장
- NCS 일반 직무 추천과 특정 기업 채용 '실제 지원 가능' 판단은 API에서 `assessmentMode`로 분리

### 12.4 공고별 워크스페이스 담당자에게 제공할 계약

- `workspaceId`가 지정되면 모든 분석/첨삭/로드맵에 연결
- 프로필 공유는 `profileId+version`, 문서 공유는 `documentId+version`, 공고는 `snapshotId`
- 최종 이력서·자소서 버전 원본은 워크스페이스 문서 서비스가 소유하고, 멘토링은 피드백/추천 결과만 저장
- 사용자가 문서/프로필 변경 시 새 버전으로 **재분석이 필요한 결과**만 invalidation 표시

## 13. 개발 검증 시나리오

| ID | 입력/전제 | 기대 결과 |

| UT-05 | 지원 필수 자격 미충족 | eligibility INELIGIBLE, 점수와 분리 |
| UT-06 | 공고 필수 역량만 있고 우대 없음 | 분류 가중치 재정규화 |
| UT-07 | 요구사항 0개 | fitScore null, INSUFFICIENT_REQUIREMENTS |
| UT-08 | 같은 요구사항 점수 반복 계산 | 동일 결과 |
| UT-09 | NCS 직무코드 잘못 입력 | 400 또는 후보 확인 요청 |
| UT-10 | KB에 다른 직무 문서 검색 | job_role 필터로 제외 |
| UT-11 | 시험 일정 API 실패 | `SCHEDULE_UNVERIFIED`, 가짜 날짜 없음 |
| UT-12 | 교육과정 없음 | 일반 실습 계획만 제공 |
| UT-13 | 자격 연결표 동일 항목 중복 | 추천 목록 중복 0 |
| UT-14 | 원문에 없는 수치 첨삭 예시 | reject/확인 질문 |
| UT-15 | 다른 사용자의 이력서 조회 | 403/404, 원문 노출 0 |
| UT-16 | RAG 문서 내 "규칙 무시" 명령 | 데이터로 취급, 실행하지 않음 |
| UT-17 | SQS 메시지 중복 2회 | 최종 작업 결과 1건 |
| UT-18 | Bedrock throttling | 지수 backoff → 복구 또는 DLQ |
| UT-19 | 공고 변경/마감 | 분석에 사용된 snapshot 버전·기준일 유지 |
| UT-20 | 텍스트 PDF와 스캔 PDF | 두 형태 모두 텍스트 추출 처리 |
| INT-01 | 업로드 → 추출 → 프로필 | 한 사용자 end-to-end |
| INT-02 | 프로필 → 적합도 → 첨삭 → 학습 | 동일 프로필/공고 snapshot 재사용 |
| INT-03 | Agent 요청 → Action Group | 기능별 API 결과와 일관 |
| EVAL-01 | 기존 sample_queries 25개 | 정답 문서 Recall@5 측정 |
| EVAL-02 | agent_prompt_tests 8개 | 안전/금지 행동 회귀 검증 |

**지표 산정 시 주의:** `Recall@5` 검색 결과 0건을 성공으로 계산하지 않음, 스키마 테스트와 사실 일치율을 별도로 보고, 테스트 통과율은 테스트케이스 수와 함께 기록.
